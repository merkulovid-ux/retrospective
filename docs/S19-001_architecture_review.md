# Анализ архитектуры безопасного ИИ-виджета (S19-001)

### Цель встречи: Всесторонне оценить предложенную архитектуру (Serverless-функция + reCAPTCHA v3 + IP Rate Limiting) с точки зрения стабильности, надежности и удобства для пользователя.

---

### Плюсы (+)

*   **Надежность и Стабильность (PO, TL):** Архитектура фундаментально решает проблему флуда, ботов и неконтролируемых расходов API. Это ключевое бизнес-требование.
*   **Масштабируемость (TL):** Созданный бэкенд-посредник (serverless-функция) можно будет легко переиспользовать для будущих ИИ-интеграций.
*   **Безопасность (TL, PMM):** Ключ от API LLM не будет храниться на клиенте, что исключает его кражу. Защита от ботов позволит собирать более чистую аналитику по использованию фичи.
*   **Пользовательский опыт (UX):** Использование невидимой reCAPTCHA v3 не создает дополнительных барьеров для легитимных пользователей. Необходимость обработки асинхронных состояний (загрузка, ошибка) заставит нас сделать интерфейс более качественным и отзывчивым.

### Минусы (-)

*   **Сложность и стоимость (PO, TL):** Мы переходим от простого статичного сайта к системе с бэкендом. Это требует дополнительных трудозатрат на разработку, настройку CI/CD, управление секретами и отладку. Возможны небольшие дополнительные расходы на serverless-платформу.
*   **Время отклика (UX):** Цепочка вызовов `Клиент -> Наш бэкенд -> Google -> LLM -> Наш бэкенд -> Клиент` длиннее, чем прямой вызов. Это может привести к заметной для пользователя задержке. **(Требует митигации)**.
*   **Риск ложных срабатываний (PMM):** reCAPTCHA может ошибочно посчитать легитимного пользователя ботом, что приведет к негативному опыту. **(Требует митигации)**.

---

### Митигация рисков:

*   **Время отклика:** На этапе реализации необходимо использовать техники оптимистичного UI. Например, показывать индикатор загрузки (спиннер) немедленно и, возможно, выводить ответ от ИИ по частям (streaming), если API это позволяет.
*   **Ложные срабатывания:** Настроить порог reCAPTCHA v3 на относительно низком уровне и вести мониторинг ошибок. Предусмотреть в UI понятное сообщение об ошибке с предложением попробовать еще раз.

---

### Итоговое решение команды:

**Утвердить предложенную архитектуру.**

Несмотря на усложнение, это единственно верный путь для создания надежного, стабильного и безопасного продукта. Преимущества значительно перевешивают недостатки, а выявленные риски можно митигировать на этапе реализации.
